Project Crawler · How it works

A machine that reads the security news so you don't have to

This crawler visits security websites and public vulnerability catalogs, saves what it finds, and files it into a database you can query. Here is the whole thing explained plainly — what it collects, how it collects it, and the rules it follows to stay welcome on other people's servers.

The short version

What it actually does

Think of it as a very patient research assistant. Every time you run it, it goes to a list of websites, asks each one “what's new since last time?”, downloads whatever it hasn't seen before, pulls the actual article text out of the surrounding clutter of menus and adverts, and stores it in a database along with the date, the source, and the web address it came from.

Alongside the articles it collects vulnerabilities — the officially catalogued security flaws that get a CVE number, like CVE-2024-21412. Those come from two government-run sources and arrive as structured data rather than prose: a severity score, a description, the affected product, the date it was published.

The end result is a single searchable pile of recent cybersecurity history: what was attacked, how, and which flaws were involved. That pile is the raw material for training a prediction model later.

The one idea that shapes everything

Two halves that aren't allowed to talk to each other

Almost every design decision comes from one rule: the part that knows about websites and the part that knows about the database are kept completely separate.

A source adapter is a small piece of code that understands one website. It knows the address of BleepingComputer's news feed, or how to read Microsoft's blog index. What it deliberately cannot do is write to the database — it has no access at all. It takes in raw downloaded bytes and hands back plain, typed descriptions of what it found.

The pipeline is the opposite: it knows everything about saving and nothing about any particular website. It takes those descriptions and writes them to Postgres.

The payoff is practical. Adding a new website means writing one small adapter and never reading a line of the saving logic. And because an adapter is just “bytes in, facts out” with no network and no database involved, it can be tested against a saved copy of a real page in a few milliseconds. The whole test suite touches the internet exactly zero times.

The journey of one article

Five stages, every single time

Everything the crawler collects travels the same five steps, whether it's a news story or a batch of two thousand vulnerability records.

01

Discover — what's out there?

The adapter produces a list of web addresses worth looking at. For a news site it reads the site's feed. For the government vulnerability database it works out how many pages of results exist and lists them all.

This stage filters by date before downloading anything. If you ask for the last two years, articles older than that are dropped here — so the crawler never pays to download something it was going to throw away.

02

Fetch — download it, politely

Each address is downloaded one at a time, with a deliberate pause between requests to the same website. This is the stage with all the manners in it, described in its own section below.

03

Archive — keep the original forever

Before anything is interpreted, the exact bytes that came back are compressed and written to disk, filed by source and date.

This is insurance, and it is worth more than it looks. The code that extracts article text from a page will get things wrong, and improving it later would normally mean re-visiting thousands of pages. Because the originals are on disk, that improvement can be re-run locally in minutes instead — no network, no waiting, no burden on anyone's server.

04

Parse — pull the facts out of the page

A downloaded web page is mostly not the article: it's navigation, related links, cookie banners, and adverts. This stage strips all that away and keeps the sentences a human would actually read, plus the title and publication date.

When extraction returns suspiciously little text, that's recorded as a warning rather than quietly saved. A page that yields 120 characters is almost always a failure, not a very short article — and a corpus quietly filling up with empty pages is far worse than one that complains.

05

Persist — write it down

The facts become rows in Postgres. Articles go in one table, vulnerabilities in another. Writing happens in batches as the crawl proceeds, so a run that dies three hours in keeps everything it had already collected.

Sources

Four different doors into the same kind of building

Every publisher offers a different way in, and the choice matters enormously — not just for speed, but for how far back you can reach.

A news feed is the obvious door, and the worst one for history: a feed holds only the most recent handful of articles, usually a few weeks' worth. No amount of patience gets you last year through a feed, because last year simply isn't in it.

A sitemap is the index at the back of the book — a machine-readable list of every page the site has ever published. It reaches all the way back, but you still have to fetch each article individually.

Some sites expose a content API, which hands over a hundred complete articles in a single response. Where one exists it is dramatically better for everyone: fewer requests for the publisher to serve, and less work for us.

Manners

How it avoids being a nuisance

The crawler is a guest on servers that other people pay for. Five rules keep it a welcome one.

  • It reads the house rules first. Websites publish a robots.txt file saying which parts automated visitors may touch. The crawler fetches it once per site, remembers it, and won't request a forbidden address. A missing file means “no restrictions” — treating it as “forbid everything” would stop the crawler on most of the internet.
  • It waits between requests. One request every two seconds to any single website, tracked separately per site. Being slow with one publisher never slows down another.
  • It says who it is. Every request carries a name and a contact address, so an administrator seeing it in their logs can find out what it is.
  • It backs off when asked. If a server replies “too many requests, wait seven seconds”, it waits exactly seven seconds. Temporary failures are retried up to four times with growing gaps; a permanent “gone” is never retried at all.
  • It gives up when told no. After five refusals in a row from one site, that site is set aside for the rest of the run.
A real example

Dark Reading was on the original list. Every article request came back 403 Forbidden — their servers deliberately refuse automated visitors. After five refusals the crawler set the site aside, exactly as designed.

It would have been easy to disguise the crawler as a web browser and carry on. That option was rejected: the publisher had made a clear decision, and working around it isn't a technical question. Dark Reading was removed from the list instead.

Efficiency

Never doing the same work twice

A crawler you can run daily has to be cheap to re-run. Three mechanisms make the second run almost free.

A fingerprint for every address

Each web address gets a short fingerprint, and the database refuses to store the same one twice. Feeds re-advertise the same articles for weeks; this makes re-running harmless rather than duplicating.

Asking “has this changed?” instead of downloading

When something is fetched, the server usually hands over a version tag. Next time, the crawler sends that tag back and asks whether anything has changed. If not, the server replies with a tiny nothing new instead of the whole page — cheaper for both sides.

A fingerprint for the content itself

The downloaded bytes get their own fingerprint. If it matches something already stored, the crawler skips extracting and saving entirely. This is what makes re-running a source that publishes one enormous file — like the government's exploited vulnerabilities catalog — cost one request instead of rebuilding 1,662 records.

$ crawler crawl --source kev first run kev: discovered=1 fetched=1 parsed=1662 failed=0 status=ok $ crawler crawl --source kev second run, unchanged kev: discovered=1 fetched=0 parsed=0 failed=0 status=ok

Failure

What happens when things go wrong

Things go wrong constantly — sites move, feeds die, servers hiccup. The crawler contains failures at three levels, so a small problem stays small.

  • One bad page is written to an error log and skipped. The run continues.
  • One bad site is set aside for the rest of the run, and the other ten carry on untouched.
  • Only the database going down stops everything — because at that point there is nowhere to put anything.
A bug this rule caught

The isolation originally had a hole. Failures were caught while downloading articles, but not while a source was working out which articles existed. Google's threat blog had quietly retired its feed, so that lookup failed — and the error escaped and killed the entire run. Four sites that hadn't had their turn yet collected nothing at all, and the log gave no hint that they'd been skipped.

The fix was to wrap the discovery step in the same protection as the download step. The site is now set aside and the crawl carries on.

Afterwards

Cleaning, and getting the data out

Sitemaps list more than articles. They also list author profiles, tag listings, and the homepage — pages that extract to a few hundred characters of menu text. A separate cleaning step removes them, along with any duplicated article text, and fills in publication dates that can be recovered from the address itself.

Cleaning shows you what it would delete before deleting anything. Across two passes it removed 359 documents, mostly The Record's author pages.

Nearly a disaster

The first attempt at finding duplicates grouped articles by the fingerprint of the downloaded file. That looked like it had found 603 duplicates. It hadn't: when one response contains a hundred articles, all hundred inherit that one file's fingerprint by design. Deleting them would have destroyed 603 perfectly good articles.

The rule now compares the fingerprint of each article's own text, which finds 15 genuine duplicates. The lesson is a general one — a number that looks alarming is worth confirming before acting on it.

Finally, the whole corpus can be written out as files. Parquet is compact and typed, so dates arrive as real dates; JSONL is one plain record per line for anything that prefers text. Every article carries its licence, so the freely redistributable material can be separated from the copyrighted news in a single filter.

$ crawler export --format parquet documents 11108 rows 20.7 MB data/export/documents.parquet vulnerabilities 116901 rows 16.3 MB data/export/vulnerabilities.parquet

Running it

The commands

crawler db ping check the database is reachable crawler sources list show every site it knows about crawler crawl fetch what's new since last time crawler backfill --since 2024-08-10 reach back into the archives crawler clean preview the junk (add --apply to remove) crawler export --format parquet write the corpus to disk crawler stats how much of what is stored

crawl is the everyday one and is safe to run as often as you like — anything already collected is skipped. backfill is the one that reaches into history, and it asks a genuinely different question: what was published in this period, rather than what has changed recently. Those return different sets, which is why they're separate commands.
